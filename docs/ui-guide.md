# UI Guide

This guide walks operators through the longue-vue web interface. No Go or Kubernetes development knowledge is assumed — the UI is the primary day-to-day surface for browsing inventory, checking EOL status, running impact analysis, and administering users and tokens.

## Overview

The interface is a single-page application served at `/ui/`. Every page shares the same chrome:

- **Left sidebar** — collapsible navigation divided into three sections: *Kubernetes* entity pages, *Cloud Infrastructure* (Virtual Machines), and *Tools* (Search, EOL, Admin). Click the hamburger button at the top of the sidebar to collapse it to icon-only mode; click again to expand.
- **Top header bar** — shows your username and a **role pill** (`admin`, `editor`, `auditor`, or `viewer`) on the right side, plus a **Sign out** button.

The SPA probes `GET /v1/auth/me` on every route navigation. If the session has expired, you are redirected to the login page automatically.

---

## Logging in

Navigate to `/ui/` (or `/`). You are redirected to the login page if no active session exists.

### Local credentials

Enter your **username** and **password** and click **Sign in**. On a first-run installation, the initial admin password is printed once to the server startup log inside a `LONGUE-VUE FIRST-RUN BOOTSTRAP` banner — check there if you have not set `LONGUE_VUE_BOOTSTRAP_ADMIN_PASSWORD`.

### OIDC

If the operator has configured an OIDC provider (`LONGUE_VUE_OIDC_ISSUER`), a **Sign in with \<label\>** button appears below the local form. Clicking it redirects your browser to the identity provider. After a successful exchange the server mints a session cookie and returns you to `/ui/`.

OIDC users are created automatically on first login with the `viewer` role. An admin must promote them if a higher role is needed.

### Forced password rotation

If your account has `must_change_password` set (for example, the bootstrapped admin account), every route redirects to the **Change Password** screen until you rotate. No other page is accessible until you submit a new password.

### Logging out

Click **Sign out** in the top-right corner. The session cookie is cleared server-side and you are returned to the login page.

## Browsing inventory

All entity list pages follow the same pattern:

1. **Filter bar** at the top — type in text fields or pick from dropdowns to narrow results. Filters apply on the server side so only matching rows are fetched.
2. **Paginated table** — rows are cursor-paginated. Use the **Next** / **Prev** controls to move through large result sets.
3. **Click a row** to open the detail page for that entity.

### Detail pages

Each detail page shows the full set of fields collected for that entity, grouped into cards. Common elements across all entity types:

- **Impact graph card** — an interactive SVG diagram showing how the entity relates to neighbouring entities (up to 2 hops by default, configurable 1–3). Click any node in the graph to navigate to that entity's detail page. The graph is generated by `GET /v1/impact/{entity_type}/{id}`.

### Cluster detail — History tab

The cluster detail page has three tabs: **Overview**, **Impact**, and **History**.

The **History** tab (ADR-0021) shows a time-travel view of cluster change events. A horizontal bar track with two range handles (A and B) lets you bracket a time window; the event list and statistics below update to show only changes within that window. Change types are colour-coded: created, changed, removed, and restored.

## Search by image or application

Path: `/search/image`  
Sidebar label: **Search**

The page is titled **"Search by image or application"** and returns two independent result sections from a single query:

- **Kubernetes workloads and pods** — matched by container image substring. Any workload or pod whose container list includes an image string containing the search term is returned.
- **Platform VMs** — matched either by image substring (the `image_id` / `image_name` fields) or by normalized application product name (entries in the VM's `applications` list).

Type a term in the search box and submit. Results appear in separate sections below the form. Click any row to go to the entity's detail page.

## EOL Inventory page

Path: `/eol`  
Sidebar label: **EOL**

The EOL Inventory page shows which software in your environment is end-of-life, approaching EOL, or still supported, as determined by the background EOL enricher (which queries endoflife.date).

### Summary cards

A row of clickable cards at the top shows counts by status: **EOL**, **Approaching EOL**, and **Supported**. Click a card to filter the table to that status; click again to clear the filter.

### Sortable table

The table has two column groups:

**What we run**

| Column | Meaning |
|--------|---------|
| Status | EOL / Approaching EOL / Supported (colour-coded badge) |
| Type | `cluster`, `node`, or `vm` — which kind of entity carries this annotation |
| Product | Software product name (e.g. `kubernetes`, `containerd`, `ubuntu`) |
| Version | The version running in your environment |
| Patch | Patch-level detail when available |
| Entity | Name of the cluster, node, or VM |
| Cluster | The cluster context (for node entities) |

**What's available**

| Column | Meaning |
|--------|---------|
| Latest Available | The newest version of the product on endoflife.date |
| EOL Date | When support ends for the running version |
| Checked | When the enricher last updated this annotation |

Rows for EOL software are highlighted in red; approaching-EOL rows in orange.

Click any column header to sort the table by that column.

## Virtual Machines page

Path: `/virtual-machines`

The VM list page has a richer filter layout than the Kubernetes pages.

### Filters block

Above a horizontal separator, the filters block provides cascading dropdowns:

- **Application** — select from the distinct normalized product names found across all non-terminated VMs.
- **App version** — narrows to a specific version of the selected application. This dropdown is only populated after an application is chosen.

Click **Search** to apply the filters. Click **Clear** to reset all filters and reload the full list. Filters are not applied automatically as you type — you must click **Search** explicitly.

Below the separator, a second set of filters covers VM-level attributes (cloud account, region, power state, name, image).

### VM detail page

The VM detail page includes an **Applications** card listing the operator-curated software entries for that VM. Each entry shows the product name, version, and optional display name and notes. Entries are managed via `PATCH /v1/virtual-machines/{id}` (editor and admin roles).

---

## Cluster ownership card

On the cluster detail page, the **Ownership & context** card shows operator-editable metadata:

| Field | Purpose |
|-------|---------|
| Owner | Team or person responsible for this cluster |
| Criticality | Importance rating (free text) |
| Notes | Freeform description or context |
| Runbook URL | Link to the operational runbook |
| Annotations | Arbitrary key-value pairs in JSONB form |

**Editors and admins** see an **Edit** toggle on the card. Click it to flip into an inline edit form, modify fields, and save. Changes are sent as a merge-patch (`PATCH /v1/clusters/{id}`); fields you leave blank are not overwritten.

**Viewers and auditors** see the same card read-only — no Edit button.

The collector never writes these fields; they are exclusively curator-facing.

## Admin section

Path: `/admin`  
Visible to: **admin** and **auditor** roles only.

The admin section is a tabbed panel. Admins see all six tabs; auditors see only the **Audit** tab.

### Users tab (admin only)

Manage local user accounts:

- **Create user** — enter a username, password, and role. The new user can log in immediately.
- **Edit user** — change username, role, or force a password rotation (`must_change_password`).
- **Disable user** — sets `disabled_at`; the user can no longer log in. The system prevents disabling the last active admin.
- **Promote / demote** — change role between `admin`, `editor`, `auditor`, and `viewer`. Demoting the last active admin is blocked with a `409 Conflict` response.
- **Status pill** — shows `Active`, `Locked`, or `Disabled`. `Locked` means the account hit the failed-login threshold (ADR-0023); hover the pill for the failed-attempt count and the lock timestamp.
- **Unlock** — appears next to the action buttons only when the account is locked. Confirms the failed-attempt count and clears `failed_login_count` + `locked_at` via `PATCH /v1/admin/users/{id}` `unlock=true`.

OIDC shadow users appear in the list. Their password field is unusable; they can only log in via the OIDC path.

### Machine tokens tab (admin only)

Issue Personal Access Tokens (PATs) for API automation:

- Click **New token** and give it a name and role preset.
- For the **vm-collector** preset, you must also select a bound **cloud account**. The issued token can only access credentials for that account.
- After creation the plaintext token is displayed **once** in a modal. Copy it immediately — it cannot be retrieved again (only the hash is stored).
- Existing tokens are listed with their prefix, creation date, and last-used time. Delete a token to revoke it immediately.

### Active sessions tab (admin only)

Lists all currently active browser sessions across all users. Click **Revoke** on any session to invalidate it immediately. Useful when a user's credentials are compromised or a device is lost.

### Cloud accounts tab (admin only)

Manage cloud-provider accounts used by the VM collector:

- View all registered accounts and their status (`pending_credentials`, `active`, `error`, `disabled`).
- Click an account to open its detail page where you can set or rotate the access key and secret key, edit curated metadata (owner, criticality, notes, runbook URL), and enable or disable the account.
- Accounts in `pending_credentials` status are highlighted — they need AK/SK before the collector can tick successfully.

### Audit tab (admin and auditor)

A paginated, newest-first log of every meaningful write operation and admin read in the system.

- **Filter** by date range, actor, HTTP method, or path.
- Each row shows timestamp, actor (user or token), source (`api`, `ingest_gw`, or `system`), HTTP method, path, and response status.
- Password, token, and secret fields are scrubbed from captured request bodies before storage and are never visible here.

Auditors land directly on this tab and cannot navigate to any other admin tab.

### Settings tab (admin only)

Runtime feature toggles that take effect immediately without a restart:

| Toggle | Effect |
|--------|--------|
| `eol_enabled` | Enables or disables the background EOL enrichment goroutine |
| `mcp_enabled` | Enables or disables the Model Context Protocol server |

## Roles in the UI

| Role | What you can do |
|------|----------------|
| `admin` | Full access: browse all inventory, write curated metadata, access all admin tabs, issue tokens, manage users |
| `editor` | Browse all inventory, write curated metadata (cluster ownership, VM applications); no admin section access |
| `auditor` | Browse all inventory read-only; access only the Audit tab in the admin section |
| `viewer` | Browse all inventory read-only; no admin section access |

The role pill in the top-right corner always shows your current role. Role changes made by an admin take effect on your next page navigation (the `/v1/auth/me` probe re-runs).
